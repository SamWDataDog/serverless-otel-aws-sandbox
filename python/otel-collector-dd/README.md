# Custom OTel Collector + Datadog exporter

Used by `otelCollectorSandbox` (see `../handler4.py` and
`../serverless.yml`) — a sidecar OTel Collector running as a Lambda
extension, with the Datadog exporter compiled in.

Neither the official `open-telemetry/opentelemetry-lambda` collector
layer nor AWS's own ADOT collector bundle the Datadog exporter. This is
a from-scratch build that does, via the [OpenTelemetry Collector
Builder](https://github.com/open-telemetry/opentelemetry-collector-releases/tree/main/distributions)
(`ocb`), plus a small Go-based Lambda extension wrapper (not bash — this
Lambda runtime's base image has no `curl`).

See the root [`FINDINGS.md`](../../FINDINGS.md) ("Round 7") for the full
investigation behind this build. This directory is source only — the
compiled collector binary, the extension binary, and the packaged layer
zip are all regenerated by the steps below, not committed.

## Go version

`extension-go/go.mod` declares `go 1.27.0` (current stable at the time
this was written). A prior pass lowered this to `1.16`, reasoning that
a high `go` directive would block a support engineer without that exact toolchain
installed. **That reasoning was wrong and has been reverted**: since Go
1.21, `GOTOOLCHAIN=auto` is the default behavior, so a `go 1.27.0`
directive causes the `go` command to download and use the required
toolchain automatically for anyone running Go 1.21 or later — the
directive was never a barrier. `1.16` was strictly worse: it predates
Go's toolchain-management mechanism entirely, so an older local
toolchain building this module would have had no automatic path to a
compatible one at all.

If you're on Go 1.21+, nothing to do — `go build`/`go install` fetches
the right toolchain on demand the first time you build this. Only a Go
installation older than 1.21, or one with `GOTOOLCHAIN=local` set,
needs a manual `go` upgrade first.

`go install go.opentelemetry.io/collector/cmd/builder@v0.137.0` in step
1 below is a separate tool with its own Go requirement, handled the
same way.

## Rebuild

```bash
# 1. Build the collector binary (cross-compiled for Lambda's linux/amd64)
go install go.opentelemetry.io/collector/cmd/builder@v0.137.0
export PATH="$PATH:$(go env GOPATH)/bin"
cd builder
GOOS=linux GOARCH=amd64 builder --config manifest.yaml
cd ..

# 2. Build the extension wrapper (same target)
cd extension-go
GOOS=linux GOARCH=amd64 go build -o ../layer/extensions/otelcol-dd-extension .
cd ..

# 3. Package the layer
mkdir -p layer/otelcol
cp builder/build/otelcol-dd-lambda layer/otelcol/
cp config.yaml layer/otelcol/
chmod +x layer/extensions/otelcol-dd-extension layer/otelcol/otelcol-dd-lambda
(cd layer && zip -qr ../otelcol-dd-layer.zip .)

# 4. Publish
aws lambda publish-layer-version \
  --layer-name otelcol-dd-sandbox \
  --zip-file fileb://otelcol-dd-layer.zip \
  --compatible-runtimes python3.11 \
  --compatible-architectures x86_64 \
  --region us-east-1
```

`otelCollectorSandbox` in `../serverless.yml` is commented out by
default — it's the only function in that stack needing a layer this
directory produces, and leaving its placeholder ARN uncommented would
fail that file's entire CloudFormation stack deploy (all five
functions), not just this one. After publishing, uncomment that
function's block and replace the placeholder with the resulting
`LayerVersionArn`.

## Debug verbosity toggle

`config.yaml` defaults to quiet: `OTELCOL_DEBUG_VERBOSITY=basic` and
`OTELCOL_LOG_LEVEL=info` (set in `../serverless.yml`'s
`otelCollectorSandbox.environment`, commented out along with the rest
of that function by default). Set both to `detailed`/`debug` there
(temporarily) to get the collector's own internal logging and every
span/metric/log body printed to CloudWatch on every invocation — useful
for confirming data reached the collector, noisy and costly to leave on.

The `debug` exporter itself is always present in all three pipelines
either way; plain OTel Collector config has no way to conditionally
omit a pipeline's exporter via env-var substitution alone, so "basic"
verbosity (one summary line per export batch) is as close to "off" as
this config format allows without a code change to the collector build
itself.

## Known gotchas

- The extension must wait for the collector's OTLP receiver port
  (`127.0.0.1:4318`) to actually accept connections before calling
  `/event/next` for the first time — otherwise Lambda ends the Init phase
  and starts invoking before the collector is ready, and the function's
  first export attempt gets `Connection refused`. See `main.go`'s
  `waitForPort`.
- `config.yaml`'s receivers bind `127.0.0.1` (loopback), not `0.0.0.0` —
  correct for a Lambda sidecar that only ever talks to code in the same
  execution environment, and what `main.go`'s own `waitForPort` already
  assumed. This wasn't always the case; if you're rebuilding from an
  older copy of this file, check which address it binds. **Not verified
  against a live deploy** — rebuild and redeploy after this change
  before trusting it over `0.0.0.0`.
